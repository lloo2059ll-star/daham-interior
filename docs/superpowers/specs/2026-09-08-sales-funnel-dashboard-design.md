# DAHAM ERP 영업 퍼널 및 계약 전환율 대시보드 설계

## 목적

DAHAM ERP에 저장된 상담, 현장방문, 견적미팅, 견적 및 계약 데이터를 재사용해 대표와 관리자용 월별 영업 퍼널을 제공한다. 사용자가 통계 숫자를 직접 입력하지 않아도 신규 문의, 현장방문, 견적미팅, 계약 실적과 단계별 전환율, 계약금액, 유입경로별 성과 및 월 목표 진행률을 확인할 수 있어야 한다.

메인 퍼널은 `신규 문의 → 현장방문 → 견적미팅 → 계약`의 네 단계로 고정한다. 견적서 생성이나 견적완료 상태만으로 견적미팅에 진입시키지 않는다.

## 기존 구조 조사 결과

- 상담 데이터는 `daham_consult_v1` 키로 `localStorage`와 Supabase `sync_data`에 배열 JSON으로 저장된다.
- 상담 레코드는 고객명, 연락처, 현장명, 주소, 평형, 예산, 입주·공사 예상일, 유입경로, 메모, 실측 정보, 현재 상태와 `history`를 이미 보유한다.
- `history`의 `milestone` 항목은 `inquiry`, `site_check`, `est_meeting`, `est_done`, `contracted` 상태와 날짜를 누적 저장한다.
- 계약 단계가 저장되면 상담의 `projId` 및 견적 프로젝트의 `consultId`로 `daham_detail_v2` 프로젝트가 연결된다.
- 견적 프로젝트는 `contractTotal`과 기존 견적 총액 계산 자료를 보유하며, `contracted` 또는 후속 상태로 계약 여부를 표현한다.
- 일정 연동은 상담 마일스톤 중 문의, 현장실측, 견적미팅을 기존 일정 데이터에 반영한다.
- 인증은 `auth.js`의 활성 프로필과 `owner`, `admin`, `staff` 역할을 사용한다. 고객 상담 모드는 `customer-view` 클래스로 내부 금액을 숨긴다.
- 회사 범위 데이터는 `companies`, `company_memberships`와 `private.is_active_company_member` 계열 정책을 사용한다.

## 데이터 원본과 호환성

### 상담 레코드

별도 영업 리드 테이블을 만들지 않고 `daham_consult_v1` 상담 레코드를 퍼널의 원본으로 사용한다. 고객 한 명은 하나의 상담 레코드로 유지하며 단계가 상승해도 이전 이력을 삭제하지 않는다.

기존 필드는 다음처럼 재사용한다.

- 고객명: `name`
- 연락처: `tel`
- 현장명: `siteName`
- 지역: `addr`에서 화면 표시용 지역을 파생하되 원본 주소를 유지
- 평형: `area`
- 공사 예상 시기: `moveDate`
- 예상 예산: `budget`
- 유입경로: `source`
- 메모: `memo`
- 현재 도달 단계: `status`와 `history`에서 파생
- 단계별 날짜: `history[type="milestone"]`
- 최초 문의일 호환값: 문의 마일스톤이 없을 때 `createdAt`
- 계약 프로젝트 연결: `projId` 또는 견적 프로젝트의 `consultId`

필요한 최소 확장 필드는 `outcomeStatus` 하나다. 값은 `in_progress`, `on_hold`, `lost`, `cancelled`로 제한하고, 값이 없는 기존 레코드는 현재 상태를 기준으로 `in_progress`로 해석한다. 기존 `cancelled` 상태는 삭제하지 않고 호환한다.

유입경로 기본 선택지는 네이버 블로그, 인스타그램, Meta 광고, 카카오, 네이버폼, 소개, 재계약, 기타다. 기존 자유 입력값은 보존하며, 기본 선택지에 없는 값도 분석 표에 독립 항목으로 집계한다. 따라서 향후 관리자가 항목을 추가해도 데이터 마이그레이션이 필요하지 않다.

### 단계 날짜 규칙

각 단계 날짜는 해당 상태의 유효한 마일스톤 중 가장 이른 날짜로 결정한다.

- 신규 문의: 최초 `inquiry`; 없으면 `createdAt`
- 현장방문: 최초 `site_check`
- 견적미팅: 최초 `est_meeting`
- 계약: 최초 `contracted`

`est_done`은 메인 퍼널에서 제외한다. 단순 견적 생성, 견적 프로젝트 생성, 견적완료 상태만으로 견적미팅 날짜를 만들지 않는다.

현재 도달 단계는 기록된 네 단계 중 가장 높은 단계다. `outcomeStatus`가 미계약 또는 취소여도 도달 단계는 유지된다. 단계가 역행하도록 현재 상태를 바꾸더라도 이미 저장된 유효 마일스톤은 통계에서 삭제하지 않는다.

### 계약 데이터와 금액

계약 건은 상담의 계약 마일스톤을 기준으로 센다. 계약금액은 연결된 견적 프로젝트의 `contractTotal`을 우선 사용하고, 값이 없으면 기존 견적 합계 계산 결과를 사용한다. 프로젝트 연결이 없거나 금액을 계산할 수 없으면 계약 건수에는 포함하되 금액은 0원으로 처리한다.

기존 견적 프로젝트가 계약 상태지만 연결된 상담에 계약 마일스톤이 없는 경우 자동으로 날짜를 추정해 저장하지 않는다. 대시보드에서 데이터 보완 필요 상태로 표시해 통계 날짜의 허위 생성을 방지한다.

## 기간 및 집계 규칙

기간 필터는 이번 달, 지난달, 최근 3개월, 올해, 월 직접 선택을 제공한다. 날짜 범위는 브라우저의 Asia/Seoul 달력 날짜를 기준으로 시작일 포함, 종료일 제외 구간으로 만든다. ISO 문자열을 UTC 날짜로 잘라 월을 판단하지 않는다.

각 단계 수는 선택 기간에 해당 단계가 실제로 발생한 건수다. 예를 들어 8월 문의가 9월에 계약되면 9월 신규 문의에는 포함하지 않고 9월 계약에는 포함한다.

계산식은 다음과 같다.

- 문의→방문: 기간 내 현장방문 수 / 기간 내 신규 문의 수 × 100
- 방문→미팅: 기간 내 견적미팅 수 / 기간 내 현장방문 수 × 100
- 미팅→계약: 기간 내 계약 수 / 기간 내 견적미팅 수 × 100
- 문의→계약: 기간 내 계약 수 / 기간 내 신규 문의 수 × 100
- 평균 계약금액: 기간 내 계약 총액 / 기간 내 계약 건수
- 계약 총액: 기간 내 계약된 상담과 연결된 계약금액 합계

분모가 0이면 0%로 반환한다. 퍼센트는 소수점 한 자리로 표시한다. 목표 진행률과 단계 전환율은 별도 필드와 별도 레이블로 표시한다.

유입경로 분석은 선택 기간의 각 단계 발생 건을 해당 상담의 `source`로 묶는다. 최종 전환율은 같은 기간의 계약 수 / 문의 수다. 계약 총액과 평균 계약금액도 같은 계약일 기준으로 계산한다.

## 월별 목표 저장

월별 목표만 정규화된 전용 테이블에 저장한다.

`public.sales_funnel_goals`

- `company_id uuid`: 회사 외래키
- `month date`: 해당 월의 첫날
- `inquiry_target integer`
- `site_visit_target integer`
- `estimate_meeting_target integer`
- `contract_target integer`
- `created_by uuid`
- `updated_by uuid`
- `created_at timestamptz`
- `updated_at timestamptz`
- 기본키: `(company_id, month)`
- 목표 값은 0 이상의 정수로 제한

행이 없는 월은 화면에서 기본값 10, 6, 4, 2를 제시한다. 사용자가 저장할 때만 해당 월의 행을 생성한다. 다른 월 행은 갱신하지 않는다.

RLS를 활성화하고 `anon` 권한은 부여하지 않는다. 활성 회사 구성원 중 owner/admin만 조회·삽입·수정할 수 있다. staff는 대시보드 자체가 노출되지 않으므로 목표 및 민감 통계 테이블에도 접근시키지 않는다. `UPDATE` 정책에는 `USING`과 `WITH CHECK`를 모두 둔다. 회사와 사용자 ID는 기존 멤버십 및 프로필에서 검증한다.

마이그레이션은 테이블, 인덱스, 최소 권한, RLS 정책을 한 파일에 포함한다. 운영 데이터는 수정하거나 초기화하지 않는다.

## 애플리케이션 구성

### 도메인 모듈

`sales-funnel-domain.js`는 UI와 저장소에 의존하지 않는 순수 함수만 제공한다.

- 상담 레코드의 단계별 최초 날짜 파생
- 기간 범위 생성과 한국 달력 날짜 판정
- 단계별 건수와 전환율 계산
- 목표 진행률 계산
- 계약금액 연결 및 합계·평균 계산
- 유입경로별 집계
- 월별 비교 데이터 생성
- 단계 카드 클릭용 고객 목록 선택
- 숫자 기반 해석 문구 생성
- owner/admin 표시 가능 여부 판정

CommonJS와 브라우저 전역을 함께 지원해 Node 테스트와 정적 HTML에서 같은 구현을 사용한다.

### Supabase 클라이언트

`sales-funnel-client.js`는 인증된 사용자로 다음 작업을 담당한다.

- 기존 `sync_data`의 상담 및 견적 프로젝트 데이터를 가져와 로컬 캐시와 병합
- 현재 회사 ID 조회
- 선택 월 목표 조회
- owner/admin 목표 저장
- 로딩, 오류 및 재시도 상태 반환

통계 원본은 기존 상담·견적 저장 흐름을 그대로 사용한다. 클라이언트는 통계 때문에 상담이나 견적 레코드를 복제하지 않는다.

### 기존 상담 화면 확장

`consult.html`과 `consult-modal.js`에는 다음 최소 변경만 한다.

- 유입경로를 기본 선택지와 기존 사용자 정의 값이 공존하는 입력으로 정리
- 결과 상태 입력 추가
- 신규 상담 저장 시 문의 마일스톤이 없으면 명시적 `inquiry` 마일스톤을 추가
- 기존 단계 이력 편집과 일정 연동 유지
- 기존 필드와 알 수 없는 JSON 속성을 보존

계약 저장 시 현재 자동 프로젝트 생성 동작을 유지한다. 기존 상담·견적·일정 기능을 임의로 리팩터링하지 않는다.

## 대시보드 UI

`erp.html` 내부 모드에 영업 퍼널 섹션을 추가한다.

상단에는 기간 필터와 목표 수정 버튼을 둔다. 목표 수정은 활성 owner/admin에게만 보인다.

메인 퍼널은 네 단계 카드로 구성한다. 각 카드는 다음 정보를 분리 표시한다.

- 단계명
- 실적 / 목표
- 목표 달성률과 진행 표시
- 신규 문의를 제외한 카드의 직전 단계 전환율

계약 총액, 평균 계약금액, 문의→계약 최종 전환율은 보조 요약 카드로 제공한다. 오렌지는 경고나 핵심 포인트에 제한하고 기존 네이비, 퍼플, 중립색을 우선한다.

카드의 실적 숫자를 누르면 해당 기간에 해당 단계에 도달한 고객 목록이 펼쳐진다. 목록은 고객명, 현장명, 최초 문의일, 현장방문일, 견적미팅일, 계약일, 유입경로, 예상 예산, 현재 상태, 메모를 제공하고 계약 행에는 계약금액을 추가한다. 상담 레코드로 이동할 때 기존 `daham_open_consult` 연결 방식을 사용한다.

유입경로 표는 유입경로, 문의, 현장방문, 견적미팅, 계약, 문의→계약 전환율, 계약 총액, 평균 계약금액을 표시한다.

월별 히스토리는 최근 월들을 행 중심의 간결한 비교표로 제공한다. 자동 해석은 목표 달성률, 가장 낮은 단계 전환율, 지난달 대비 문의 증감처럼 계산값을 한두 문장으로 읽는 수준에 제한한다.

반응형 레이아웃은 다음 기준을 따른다.

- PC: 네 단계 퍼널 4열, 요약 카드와 분석 표 병렬 활용
- 태블릿: 퍼널 2열, 분석 영역 1열
- 모바일: 퍼널과 요약을 1열, 표는 중요 열 우선 카드형 또는 안전한 가로 스크롤

`body.customer-view`에서는 영업 퍼널, 목표, 계약금액, 전환율 및 분석 영역 전체를 숨긴다. staff에게도 메뉴와 콘텐츠를 렌더하지 않는다. DOM을 숨기는 것에 더해 DB 정책으로 목표 데이터 접근을 차단한다.

## 로딩과 오류 처리

- 로딩 중에는 0을 확정값처럼 보이지 않도록 로딩 상태를 표시한다.
- Supabase 동기화 실패 시 기존 로컬 데이터는 삭제하거나 덮어쓰지 않는다.
- 목표 조회 실패 시 기본 목표를 임시 표시하되 저장된 값으로 오인되지 않도록 안내한다.
- 목표 저장 실패 시 화면의 확정 목표를 변경하지 않고 오류와 재시도를 제공한다.
- 손상된 날짜, 중복 마일스톤, 연결되지 않은 프로젝트는 개별 레코드를 건너뛰거나 데이터 보완 대상으로 표시하며 전체 대시보드를 중단하지 않는다.
- `NaN`과 `Infinity`는 도메인 계층에서 차단한다.

## 테스트 전략

모든 도메인 동작은 테스트를 먼저 작성하고 예상 이유로 실패하는 것을 확인한 뒤 구현한다.

필수 계산 테스트:

1. 문의 10, 방문 7, 미팅 3, 계약 2 → 70.0%, 42.9%, 66.7%, 20.0%
2. 모든 건수 0 → 모든 비율이 유효한 0이며 `NaN`/`Infinity` 없음
3. 미팅 3, 계약 2 → 66.7%
4. 9월과 10월 단계 이벤트가 섞이지 않음
5. 9월 목표 수정이 8월 목표에 영향을 주지 않음

추가 자동 테스트:

- 각 단계의 최초 마일스톤만 사용
- 문의 이력 없는 기존 레코드의 `createdAt` 호환
- `est_done` 및 견적 생성만으로 미팅을 세지 않음
- 이탈·취소 레코드의 과거 도달 단계 유지
- 계약 프로젝트 금액 우선순위와 0원 안전 처리
- 유입경로별 건수, 전환율, 합계 및 평균
- Asia/Seoul 월 경계
- owner/admin 표시 및 staff 차단
- 고객 상담 모드에서 민감 영역 숨김
- 모바일, 태블릿, PC CSS 레이아웃 마커
- 마이그레이션의 RLS, grant/revoke, 회사 격리, staff 거부, owner/admin 허용
- 기존 상담, 일정, 견적, 계약 테스트 전체 회귀

가능한 경우 로컬 Supabase에 마이그레이션을 적용하고 SQL 보안 테스트 및 목표 저장·새로고침·월 독립성을 검증한다. 로컬 DB 환경이 없으면 정적 SQL 테스트와 애플리케이션 테스트를 완료하고 실제 DB 적용 검증을 배포 전 추가 작업으로 명시한다.

## 완료 및 배포 조건

완료 전 다음을 확인한다.

- 전체 Node 테스트 통과
- 프로젝트에 존재하는 lint/type 검사 실행 또는 해당 스크립트가 없음을 명시
- 상담·현장·견적·계약·일정·발주·정산 관련 기존 테스트 회귀 통과
- 필수 계산 사례 통과
- Supabase 목표 저장 후 새로고침 유지 및 월 독립성 확인
- owner/admin/staff 및 고객 상담 모드 노출 확인
- 모바일·태블릿·PC 레이아웃 확인
- 운영 데이터 삭제나 초기화가 없음

배포는 자동 수행하지 않는다. 결과 보고에는 수정 파일, DB 변경, 퍼널 데이터 생성 위치, 계산식, 기존 기능 연동, 테스트 결과, 배포 단계 및 남은 제한사항을 포함한다.
