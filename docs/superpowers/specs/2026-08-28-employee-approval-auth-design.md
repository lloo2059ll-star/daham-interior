# 직원 승인 기반 인증 및 Supabase 연동 설계

## 목적

기존 정적 HTML 업무 시스템과 localStorage 기반 데이터 흐름을 유지하면서 Supabase Auth 및 `profiles` 권한 모델을 모든 페이지의 공통 접근 제어로 사용한다. 신규 직원은 이름, 이메일, 비밀번호로 가입한 뒤 관리자 승인 대기 상태가 되며, 활성화된 직원만 내부 페이지와 `sync_data`에 접근할 수 있다. 대표(`owner`)는 별도 직원관리 화면에서 직원 승인, 사용중지, `staff`/`admin` 역할 변경을 수행한다.

## 확정된 제약

- 대상 저장소는 `lloo2059ll-star/daham-interior`이며 기존 정적 HTML 구조를 유지한다.
- Supabase DAHAM 프로젝트의 기존 `profiles`, `sync_data`, 트리거 및 RLS를 사용한다.
- 역할은 `owner`, `admin`, `staff`이며 신규 가입자는 `staff`, `is_active = false`이다.
- 직원관리 UI는 `owner`에게만 노출하고 진입을 허용한다.
- 브라우저에는 기존 publishable key만 두며 `service_role` 또는 secret key를 추가하지 않는다.
- 고객, 현장, 견적 등 기존 데이터와 localStorage 키를 삭제하거나 초기화하지 않는다.
- localStorage는 계속 로컬 캐시와 기존 화면 간 데이터 전달 수단으로 사용한다.

## 현재 구조와 문제점

저장소는 빌드 과정 없는 정적 HTML 애플리케이션이다. `auth.js`가 로그인, 토큰 갱신, 프로필 조회와 내부 페이지 리다이렉트를 담당하고 각 업무 페이지가 자체 localStorage 데이터 모델과 일부 Supabase 동기화 코드를 가진다.

현재 `auth.js`는 비활성 프로필을 모두 “비활성화”로 처리하고 가입 직후 승인 대기 안내를 제공하지 않는다. 인증 판정이 비동기여서 내부 화면이 잠시 보일 수 있으며, 캐시된 프로필이 있으면 페이지 진입 때 최신 `is_active` 값을 확인하지 않을 수 있다. 일부 동기화 코드는 다른 Supabase 프로젝트를 참조하거나 사용자 JWT 없이 publishable key를 Authorization 값으로 사용하므로 DAHAM RLS와 일치하지 않는다.

## 선택한 접근

공통 `auth.js`를 인증 경계와 Supabase 접근 어댑터로 강화한다. 각 업무 페이지의 데이터 구조는 바꾸지 않고, 기존 Supabase 클라이언트 또는 직접 `fetch` 호출이 현재 사용자 access token을 사용하도록 연결한다. 이 접근은 정적 페이지를 SPA로 재작성하거나 페이지마다 중복 가드를 추가하는 것보다 변경 범위와 회귀 위험이 작다.

## 인증 흐름

### 회원가입

`login.html`에 로그인과 직원가입 탭을 둔다. 가입 폼은 이름, 이메일, 비밀번호, 비밀번호 확인을 받는다. `auth.js`는 Supabase `/auth/v1/signup`에 `display_name`과 `username` 메타데이터를 전달한다.

가입 응답에 세션이 포함되어도 내부 페이지로 보내지 않는다. 생성된 세션으로 프로필을 확인할 수 있으면 승인 대기 상태를 확인한 뒤 Supabase 로그아웃을 요청하고 로컬 인증 캐시를 지운다. 이메일 확인이 필요한 구성에서는 인증 메일 확인 안내를 승인 대기 메시지에 함께 표시한다. 사용자에게는 최종적으로 “가입이 완료되었습니다. 관리자 승인 대기 중입니다.”를 명확히 보여 준다.

### 로그인

비밀번호 로그인 성공 후 반드시 해당 사용자의 `profiles` 행을 조회한다. 프로필이 없으면 세션을 폐기하고 관리자 문의 메시지를 표시한다. `is_active = false`이면 세션을 폐기하고 “관리자 승인 대기 중입니다.”를 표시한다. 활성 프로필만 로그인 완료로 간주하고 `index.html`로 이동한다.

### 내부 페이지 보호

`login.html`을 제외한 모든 HTML은 보호 대상이다. `auth.js`는 문서 파싱 초기에 화면을 숨기고 다음 순서로 검사한다.

1. 저장된 access/refresh token 존재 여부 확인
2. 만료 임박 access token 갱신
3. 매 페이지 진입 시 현재 사용자 `profiles` 행 재조회
4. `is_active = true` 확인
5. 성공 시 화면 표시, 실패 시 인증 캐시 삭제 후 `login.html` 이동

`signup.html`은 기존 진입 링크를 제거하고 `login.html`로 이동시키는 호환 페이지로 남긴다. 승인 대기나 사용중지로 강제 로그아웃할 때 localStorage의 업무 데이터는 삭제하지 않고 인증 전용 키만 삭제한다.

## 공통 Supabase 연동

`auth.js`는 DAHAM Supabase URL, publishable key, 현재 access token을 반환하는 명시적 인터페이스를 제공한다. 업무 페이지의 Supabase 클라이언트는 `global.headers.Authorization` 또는 동등한 클라이언트 옵션으로 사용자 JWT를 전달한다. 직접 REST를 호출하는 페이지는 요청 시점의 JWT로 헤더를 만든다.

기존 localStorage 우선 동작은 유지한다. 로컬 저장, 타임스탬프 비교, 긴급 백업, 개별 프로젝트 병합 및 삭제 로직의 의미는 바꾸지 않는다. 이 작업은 인증된 동기화 경로만 정렬하며 `sync_data`나 localStorage를 일괄 삭제, 초기화, 재마이그레이션하지 않는다.

기존에 다른 Supabase 프로젝트 URL과 publishable key를 사용하는 고객·공유 화면 코드는 DAHAM 업무 데이터 접근 여부를 구분해 처리한다. 내부 업무 데이터 동기화는 DAHAM 프로젝트와 사용자 JWT로 통일하고, 공개 공유 기능이 실제로 별도 프로젝트에 의존하는 경우 그 공개 기능의 기존 연결은 유지한다.

## 직원관리 화면

새 `employees.html`은 공통 인증 가드를 통과한 후 현재 사용자가 `owner`인지 다시 검사한다. owner가 아니면 `index.html`로 이동하고 안내한다. 대시보드 메뉴의 직원관리 링크도 owner에게만 표시한다.

화면은 `profiles`에서 `id`, `email`, `username`, `display_name`, `role`, `is_active`를 조회해 이름, 이메일, 역할, 상태를 보여 준다. 각 비-owner 행에는 다음 동작을 제공한다.

- 승인 대기 또는 중지 계정을 `is_active = true`로 변경
- 활성 계정을 `is_active = false`로 사용중지
- 역할을 `staff` 또는 `admin`으로 변경

owner 행은 현재 대표 계정으로 표시하며 역할 및 활성 상태 변경 컨트롤을 비활성화한다. 변경은 단일 필드 PATCH 후 서버에서 목록을 다시 조회해 확인한다. RLS 거부, 네트워크 오류, 이미 변경된 행은 화면 내 오류 메시지로 표시하며 낙관적 상태를 남기지 않는다.

## 보안

- 권한 판단에 사용자 편집 가능한 `user_metadata`를 사용하지 않고 `profiles`의 RLS 보호 필드를 사용한다.
- 프론트 요청에는 publishable key와 현재 사용자 JWT만 사용한다.
- `service_role`, secret key, 관리자 비밀번호를 저장소나 브라우저 번들에 포함하지 않는다.
- UI의 owner 제한은 사용성 계층이며, 실제 데이터 변경 권한은 기존 RLS가 최종 강제한다.
- 캐시된 프로필만 신뢰하지 않고 내부 페이지 진입과 관리 작업 전에 서버 프로필을 재조회한다.
- 로그아웃 및 승인 거부 시 업무 localStorage는 보존하고 인증 키만 제거한다.

## 오류 처리

- 네트워크 일시 오류와 인증 실패를 구분한다. 인증 실패는 로그인으로 이동시키고, 네트워크 오류는 데이터 손실 없이 재시도 안내를 표시한다.
- 토큰 갱신 실패 시 인증 캐시만 제거한다.
- 가입 폼은 이메일 형식, 이름 필수, 비밀번호 8자 이상, 비밀번호 일치를 클라이언트에서 검증한다.
- 직원관리 PATCH 실패 시 기존 화면 값을 유지하고 실패 메시지를 표시한다.
- 동기화 실패는 기존 localStorage 저장을 롤백하지 않는다. 로컬 데이터가 계속 원본 캐시로 남도록 기존 동작을 보존한다.

## 테스트 전략

Node 내장 테스트 러너와 가벼운 브라우저 전역 스텁을 사용해 외부 패키지 설치 없이 다음을 검증한다.

- 가입 입력 검증, 승인 대기 결과, 가입 직후 세션 정리
- 로그인 시 미승인/사용중지/프로필 누락 차단과 활성 직원 허용
- 보호 페이지에서 무세션, 만료 세션, 비활성 프로필 리다이렉트
- 모든 내부 HTML의 `auth.js` 포함 및 login 이외 공개 페이지 부재
- owner만 직원관리 API와 화면에 접근하고 owner 자신의 변경은 차단
- 직원 승인, 사용중지, `staff`/`admin` 변경 요청 형식
- DAHAM `sync_data` 요청이 현재 access token을 사용
- 기존 localStorage 업무 키를 인증 코드가 삭제하지 않음
- 저장소 전체에서 `service_role` 및 secret key가 존재하지 않음

정적 테스트 후 로컬 HTTP 서버에서 주요 화면을 열어 콘솔 오류, 레이아웃, 리다이렉트 동작을 확인한다. 최종 검증은 전체 테스트 실행, 변경 파일 diff 검토, 비밀 키 스캔, Git 상태 확인 순서로 수행한다.
