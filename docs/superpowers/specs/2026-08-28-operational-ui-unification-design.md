# 운영 페이지 UI 통합 설계

## 목적

현재 대시보드와 현장 견적 계열이 사용하는 시각 언어를 기준으로 실제 운영 페이지의 레이아웃과 UI를 통일한다. 기능, Supabase 연동, 권한, CRUD, 데이터 구조, URL, 기존 업무 흐름 및 인쇄 결과는 변경하지 않는다.

## 수정 금지 기준 화면

다음 파일은 디자인 참고용으로만 읽으며 바이트 단위로 수정하지 않는다.

- `index.html`
- 모든 `estimate*.html`

작업 시작 시 위 파일의 SHA-256 해시를 기준값으로 기록하고 작업 완료 후 동일함을 검증한다. 이 파일들이 현재 불러오는 `v2-theme.css`, `v2-suite.css`, `v2-suite.js`도 수정하지 않는다. 따라서 공통 자산 변경으로 기준 화면이 간접적으로 달라지는 일도 없다.

## 작업 대상

실제 운영에 사용하는 다음 페이지에만 새 공통 시각 계층을 적용한다.

### 관리형 화면

- `contacts.html`
- `as.html`
- `order.html`
- `payment.html`
- `employees.html`
- `worklog.html`
- `photos.html`

### 문서 및 출력 화면

- `contract.html`

`signup.html`은 즉시 `login.html#signup`으로 이동하는 호환 기능을 유지하며, 이동 실패 시 보이는 최소 화면만 공통 스타일에 맞춘다.

## 명시적 제외 대상

- `consult-demo.html`
- `design-demo.html`
- `index.prototype.html`

데모 및 프로토타입은 이번 작업에서 수정하지 않는다.

## 선택한 접근

기존 기준 화면이 참조하는 공통 파일은 그대로 보존하고, 운영 페이지만 참조하는 새 공통 스타일 파일을 추가한다. 예를 들어 `operations-ui.css`가 디자인 토큰과 공통 컴포넌트를 담당하고, 필요한 경우 아주 작은 페이지별 범위 규칙을 같은 파일 안에서 명시적인 body 클래스 아래 둔다.

각 HTML에는 새 스타일 링크와 시각적 범위를 나타내는 클래스만 최소한으로 추가한다. 기존 요소 ID, `name`, `data-*`, `onclick`, 스크립트 순서 및 데이터 렌더링 컨테이너는 유지한다. JavaScript로 화면 골격을 동적으로 바꾸거나 기능 요소를 재생성하지 않는다.

## 디자인 시스템

### 토큰

대시보드와 견적 화면에서 이미 사용 중인 값을 새 운영 전용 CSS 변수로 옮긴다.

- 배경: 옅은 회색 `#f6f7fb` 계열
- 카드: 흰색, 옅은 경계선, 낮은 그림자
- 텍스트: 짙은 남색 계열과 중간 회색 보조 텍스트
- 내비게이션: `#18223b` 및 `#233052` 계열
- 주요 동작: 보라색 `#6f5be7` 계열
- 상태: 초록, 주황, 빨강 계열
- 모서리: 입력/버튼 9px 전후, 카드/모달 14~18px
- 간격: 4px 기반의 일관된 여백 체계

새 변수 이름에는 운영 화면 전용 접두사를 사용해 기존 견적 페이지의 전역 변수와 충돌하지 않게 한다.

### 공통 컴포넌트

- 상단 툴바와 페이지 제목 영역
- 콘텐츠 최대 폭과 반응형 좌우 여백
- 카드와 요약 카드
- 테이블 헤더, 행, 행 동작 영역 및 빈 상태
- 기본/주요/위험/보조 버튼
- 상태와 역할 배지
- 텍스트 입력, 선택, 날짜, 검색 및 필터 영역
- 모달 배경, 본문, 헤더와 하단 동작 영역
- 토스트, 안내, 오류 및 로딩 상태

기존 클래스가 페이지마다 다르므로 공통 스타일은 새 body 범위 클래스 아래에서 기존 클래스들을 어댑터로 매핑한다. 마크업을 전면 교체하지 않는다.

## 페이지 유형별 적용

### 관리형 화면

툴바, 제목/설명, 주요 동작, 검색과 필터, 데이터 카드 및 표의 시각적 위계를 대시보드와 맞춘다. 모바일에서는 표가 잘리거나 기능 버튼이 사라지지 않도록 기존 구조에 맞춰 가로 스크롤 또는 행 재배치를 사용한다. 권한에 따른 버튼 표시 로직은 그대로 둔다.

### 문서 및 출력 화면

화면상 편집 툴바, 입력 영역, 미리보기 주변 배경과 동작 버튼만 공통 스타일로 맞춘다. 문서 본문 크기, 용지 규격, 인쇄 여백, 페이지 나눔 및 `@media print` 규칙은 변경하지 않는다. 새 공통 CSS는 `@media print`에서 화면 장식에 영향을 주지 않도록 명시적으로 중립화한다.

### 로그인 화면

대시보드의 색상과 견적 화면의 카드·입력·버튼 스타일을 사용하되 로그인, 회원가입, 승인 대기, 오류 메시지, 리다이렉트 흐름 및 DOM 식별자는 유지한다.

## 기능 보존 원칙

- Supabase URL, 키, 쿼리, 테이블, RLS 연계 코드를 변경하지 않는다.
- 인증 및 역할 판정 코드를 변경하지 않는다.
- CRUD 함수, 이벤트 핸들러, 저장 형식과 localStorage 키를 변경하지 않는다.
- 링크 대상, URL 해시와 페이지 전환을 변경하지 않는다.
- 기능 요소를 숨기거나 새 권한 동작을 만들지 않는다.
- 기존 인쇄 결과를 변경하지 않는다.

## 검증 전략

### 변경 경계

- 작업 전후 `index.html`과 모든 `estimate*.html`의 SHA-256 일치
- `v2-theme.css`, `v2-suite.css`, `v2-suite.js`의 SHA-256 일치
- 제외된 데모/프로토타입 세 파일의 SHA-256 일치
- 변경 파일 목록이 확정된 운영 페이지와 새 공통 CSS에 한정되는지 확인

### 자동 회귀 테스트

- 기존 전체 테스트 실행
- HTML 및 JavaScript 정적 검사
- 인증, 권한, 상담 삭제를 포함한 기존 CRUD 테스트
- Supabase 요청과 localStorage 키 보존 테스트
- 링크, ID, 이벤트 핸들러 및 중요 폼 필드가 유지되는지 비교
- 문서 페이지의 인쇄 관련 규칙과 출력 요소가 유지되는지 검사

### 브라우저 검증

- 로그인과 회원가입 상태 화면
- 상담, 거래처, A/S, 발주, 계약/결제, 직원, 업무일지, 사진, 일정, 단가 화면
- 문서 편집 및 인쇄 미리보기
- 데스크톱과 모바일 폭의 레이아웃
- owner/admin/staff별 기존 버튼 가시성과 동작
- 배포 후 실제 도메인에서 자산 로딩, 콘솔 오류 및 주요 페이지 접근

## 배포

검증을 통과한 변경만 기능 브랜치에 커밋한다. 이후 GitHub API 또는 허용된 비-HTTPS Git 전송 경로로 원격에 반영하고 `main`에 병합한다. GitHub Pages 배포 성공을 확인한 뒤 실제 사이트에서 새 공통 CSS와 주요 운영 페이지를 다시 확인한다.
