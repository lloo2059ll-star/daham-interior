# 다함 인테리어 네이버 블로그 견적문의 폼 설계

## 목적

네이버 블로그 방문자가 별도 상담 페이지에서 견적 정보를 편하게 남기고, 접수 결과가 다함 ERP의 `상담 / 현장실측`에 신규 상담으로 자동 등록되며, 알림을 허용한 승인 직원 전원에게 즉시 푸시되게 한다.

기존 공개 문의 저장 경로와 ERP 상담 데이터를 재사용한다. 새 폼 때문에 별도의 고객 관리 체계를 만들지 않는다.

## 확정된 사용자 경험

### 시각 방향

- 승인 시안은 `visual-style-v3.html`의 프리미엄 에디토리얼 방향이다.
- 주조색은 아이보리, 모래빛 베이지, 먹색이다.
- 둥근 앱 카드와 과한 테두리를 피하고 얇은 선, 넓은 여백, 정돈된 타이포그래피를 사용한다.
- 한글 제목 자간은 약 `-0.04em`, 본문은 약 `-0.015em`을 기준으로 하되 실제 사용 폰트 렌더링을 보고 미세 조정한다.
- 영업 문구보다 다함 인테리어의 시공 원칙을 먼저 보여준다.
- 모바일 블로그 유입이 핵심이므로 360px 폭부터 입력과 버튼이 편안하게 보이도록 설계한다.

### 화면 흐름

한 화면에 모든 입력란을 밀어 넣지 않고 세 단계로 나눈다.

1. 기본 정보: 성함, 연락처
2. 현장 정보: 현장 주소, 아파트·현장명, 평형, 전체 공사·부분 공사, 예산, 희망 공사 시점
3. 상담 내용: 자유 문의, 개인정보 수집·이용 동의, 최종 제출

상단에는 `01 기본 정보 — 02 현장 정보 — 03 상담 내용` 진행 상태를 보여준다. 단계 이동 전 현재 단계의 필수값만 검증하며, 이전 단계로 돌아가도 입력값을 유지한다.

### 완료와 오류

- 제출 중에는 버튼을 비활성화해 중복 접수를 막는다.
- 성공은 DB 저장과 ERP 자동 등록 트리거가 함께 성공했을 때만 표시한다.
- 성공 문구는 `문의가 접수되었습니다. 확인 후 순서대로 연락드리겠습니다.`로 한다.
- 오류 시 작성 내용을 유지하고 재시도할 수 있게 한다.
- 전화 상담 번호 `010-2059-0347`을 보조 수단으로 제공한다.

## 데이터 흐름

```text
네이버 블로그 링크
  → 블로그 전용 문의 페이지
  → public.website_inquiries INSERT
  → private DB trigger
      ├─ ERP daham_consult_v1에 상담문의 상태로 추가
      └─ activity_events + notification_outbox 생성
  → 푸시 발송 작업자
  → 알림을 허용한 승인 직원 전원의 휴대전화
```

공개 브라우저는 publishable key로 `website_inquiries`에 INSERT만 한다. ERP 데이터와 알림 테이블을 직접 읽거나 쓰지 않는다.

## ERP 상담 변환

신규 문의는 다음 기준으로 ERP에 추가한다.

- `status`: `inquiry`
- `consultTitle`: `네이버 블로그 견적 문의`
- `source`: `네이버 블로그`
- `websiteInquiryId`: 공개 문의 UUID
- `createdAt`, `updatedAt`: 문의 생성 시각
- 이름, 연락처, 주소, 현장명, 평형, 예산, 희망 공사일, 문의 내용을 기존 ERP 필드에 매핑
- `history`: 최초 `inquiry` 마일스톤과 `네이버 블로그 견적 문의 자동 접수` 이력을 포함

`websiteInquiryId`로 중복을 방지하고 기존 `daham_consult_v1` 배열 갱신 시 행 잠금과 advisory lock을 유지해 동시 접수 덮어쓰기를 막는다.

## 전 직원 푸시 알림

ERP 상담 생성과 같은 DB 트랜잭션에서 활동 이벤트와 알림 발송함 레코드를 만든다. 공개 사용자가 인증 직원 전용 `publish_activity` RPC를 호출하게 만들지 않는다.

알림 대상은 같은 회사의 승인된 직원 중 활성 푸시 구독을 가진 전원이다.

- 제목: `신규 상담 · 네이버 블로그`
- 본문: `{고객명} / {지역 또는 현장명}`
- 이동 주소: `consult.html`의 해당 상담 식별자를 포함한 동일 출처 상대 URL
- 엔터티 유형: `consultation`
- 액션: `create`
- 중복 키: `website-inquiry:{websiteInquiryId}`

개인정보 노출을 줄이기 위해 잠금 화면 알림 본문에는 전화번호, 상세 주소, 자유 문의 내용을 넣지 않는다.

상담 저장 성공 후 푸시 전송이 일시적으로 실패해도 상담은 유지한다. `notification_outbox`는 실패 상태와 오류를 기록하고 기존 발송 작업자의 재시도 흐름을 사용한다.

## 보안과 개인정보

- `website_inquiries`는 RLS를 유지하며 `anon`에는 INSERT만 허용한다.
- `anon`과 미인증 사용자는 문의 SELECT·UPDATE·DELETE, ERP, 활동 이벤트, 알림 발송함에 접근할 수 없다.
- 공개 페이지에는 service role 또는 secret key를 넣지 않는다.
- 이름, 연락처, 입력 길이, 허용된 공사 범위, 개인정보 동의, 빈 honeypot을 클라이언트와 DB 제약 양쪽에서 검증한다.
- DB 트리거는 비공개 스키마에 두고 빈 `search_path`와 완전 수식 객체명을 사용한다.
- 보안 정의자 함수의 직접 실행 권한은 `public`, `anon`, `authenticated`에서 회수한다.
- 알림 이동 주소는 ERP 내부의 동일 출처 상대 URL만 허용한다.

## 구현 접근 방식 비교

### A. 공개 폼이 ERP와 알림 API를 각각 호출

구현은 단순해 보이지만 공개 브라우저에 과도한 권한이 필요하고, ERP 등록과 알림 사이에 불일치가 생길 수 있어 사용하지 않는다.

### B. 기존 문의 트리거에서 ERP와 알림 이벤트를 함께 생성 — 채택

기존 `website_inquiries → ERP` 원자적 변환을 유지하면서 알림 이벤트를 같은 서버 측 흐름에 추가한다. 공개 권한을 늘리지 않고 중복과 실패를 통제할 수 있다.

### C. 별도 서버리스 API가 모든 처리를 담당

확장성은 좋지만 현재 정적 사이트에 새 서버 경로, 인증, 운영 지점을 추가한다. 현재 규모와 기존 구조에는 불필요하므로 채택하지 않는다.

## 변경 범위

- `inquiry.html`: 승인된 3단계 화면 구조와 문구
- `inquiry.css`, `inquiry-overrides.css`: 승인된 색상, 타이포그래피, 반응형 레이아웃
- `inquiry.js`: 단계 이동, 단계별 검증, 중복 제출 방지, 결과 상태
- `website-public-domain.js`: 블로그 유입 정보와 필드 정규화
- 새 Supabase migration: ERP 매핑 문구 및 신규 상담 활동·알림 발송함 생성
- 테스트: 도메인, UI, DB 보안, ERP 변환, 알림 중복 키와 민감정보 제외

## 검증 기준

1. 데스크톱과 360px 모바일에서 가로 스크롤 없이 세 단계를 사용할 수 있다.
2. 필수값이 없으면 해당 단계에서 진행하지 않으며 정확한 입력란을 안내한다.
3. 정상 제출 한 건이 `website_inquiries` 한 행과 ERP 신규 상담 한 건만 만든다.
4. ERP 상담의 출처가 `네이버 블로그`, 상태가 `inquiry`로 표시된다.
5. 동일 문의 UUID 재처리는 ERP 상담이나 푸시를 중복 생성하지 않는다.
6. 알림 허용 상태인 승인 직원 전원의 구독이 발송 대상이 된다.
7. 알림에는 전화번호, 상세 주소, 자유 문의가 노출되지 않는다.
8. 알림을 누르면 해당 ERP 상담으로 이동한다.
9. 푸시 발송 실패가 상담 접수를 되돌리지 않으며 재시도 가능한 상태로 남는다.
10. 익명 사용자가 공개 문의 외 ERP·알림 데이터를 읽거나 변경할 수 없다.

## 범위 제외

- 카카오 알림톡 또는 SMS
- 고객에게 접수 완료 메시지 발송
- 직원별 알림 종류 선택
- 네이버 폼 사용
- 네이버 블로그 본문 편집과 링크 삽입은 폼 배포와 실제 URL 확인 이후 별도 단계에서 진행
