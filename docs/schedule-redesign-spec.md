# 일정관리 개편 설계

## 목표와 보호 범위

일정 화면을 계약 현장 카드, 전체 월간 일정, 일반 일정, 견적 기반 공정 후보 생성 중심으로 개편한다. 견적 데이터는 읽기 전용으로만 사용하며 견적·계약·직원·권한·상담·결제·AS의 계산, 저장, URL, 데이터 구조와 기존 업무 흐름은 변경하지 않는다. 기존 일정과 수동 현장은 삭제하거나 초기화하지 않는다.

## 확인된 운영 데이터 계약

- 견적 프로젝트 저장소는 `daham_detail_v2`이고 프로젝트의 안정 ID는 `project.id`다.
- 계약서는 별도 계약 ID를 만들지 않는다. 견적에서 전달된 `projId`를 `_linkedProjId`로 보존하고 계약금액을 같은 `project.id`의 `contractTotal`에 기록한다.
- 일정 현장은 `daham_schedule_v1` 배열이며 정식 계약 현장의 연결키는 기존 `estimateId` 필드에 저장된 견적 프로젝트 ID다. 구현 내부에서는 의미를 명확히 하기 위해 `linkedProjectId`로 정규화해 다루되 저장 호환을 위해 기존 `estimateId`를 유지한다.
- 활성 계약 현장은 견적의 표준 `status`가 `contracted` 또는 `construction`인 프로젝트다. 과거 데이터는 `contracted === true`를 호환 판정한다. `completed`는 신규 자동 생성 대상에서 제외한다.
- 견적 선택 항목은 `section|sub|detail` 키와 0보다 큰 수량으로 판정한다. 구형 `sectionIndex_itemIndex` 키는 고정 카탈로그 인덱스로 정규 키에 변환한다.
- 사용자 권한은 `auth.js`가 캐시한 활성 profile의 `role`을 사용하며 대표는 `role === "owner" && is_active === true`다.

## 하위 호환 저장

기존 `daham_schedule_v1` 배열은 구조 변환 없이 현장과 공사 일정 전용으로 유지한다. 일반 일정은 별도 배열 키 `daham_schedule_general_v1`에 저장하며 Supabase `sync_data`에도 동일 이름의 별도 행으로 동기화한다. 두 저장소는 독립적으로 pull/push하고 한쪽의 오류가 다른 쪽의 로컬 동작을 막지 않는다.

기존 현장과 일정의 ID, 개수, 내용은 유지한다. 기존 `migrate()`의 이름·기간 기반 중복 삭제는 제거하고 누락된 선택 필드만 읽을 때 기본값으로 해석하는 비파괴 정규화로 교체한다.

기존 수동 현장은 `legacy-manual`로 해석해 조회와 기존 일정 편집을 유지한다. 신규 수동 현장 생성 버튼과 흐름은 제거한다. 문자열 이름이나 주소를 이용해 계약 현장과 자동 결합하지 않는다.

## 일정 도메인 모듈

새 `schedule-domain.js`는 DOM과 저장소에 의존하지 않는 순수 함수로 다음을 담당한다.

- 프로젝트 상태와 안정 ID 기반 계약 현장 선택 및 중복 방지
- 견적 수량 키 정규화와 포함 항목 판독
- 중앙 공정 규칙 레지스트리와 후보 생성
- 후보 정렬, 체크 해제, 사용자 추가·이름 변경 결과 검증
- 기간 및 동일 작업자 충돌 검사
- 기존 배열 비파괴 정규화

`schedule.html`은 화면, 로컬 저장, Supabase 동기화, 권한 확인을 담당한다.

## 견적 공정 규칙

중앙 규칙은 정확한 정규 항목 ID 집합과 조건으로 정의하며 부분 문자열 추측으로 공정을 생성하지 않는다.

- 전기/조명 포함: `전기/조명 1차`, `전기/조명 2차`
- 시스템에어컨 포함: `에어컨 1차`, `에어컨 2차`
- 새 강마루 포함: `마루 시공`
- 새 강마루와 기존 강화마루/강마루 철거가 모두 포함: `마루 철거`, `마루 시공`
- 동일 현장의 거실욕실, 안방욕실, 현관, 주방, 베란다 타일 항목: `타일작업` 하나
- 거실욕실과 안방욕실 천장 항목: `욕실 천장작업` 하나
- 두 욕실의 양변기, 세면기, 수전, 샤워기, 욕실기구, 액세서리 항목: `도기세팅` 하나

욕실 우선순위는 `타일작업 → 욕실 천장작업 → 도기세팅`으로 고정한다. 세 공정은 서로 합치지 않으며 각 규칙 ID당 후보 하나만 만든다.

## 공정 후보 흐름

정식 계약 현장에서 `견적에서 공정 불러오기`를 누르면 현재 연결된 프로젝트 ID의 현재 견적 객체 하나만 읽는다. 후보는 저장 전에 체크리스트 모달에서 체크 해제, 사용자 공정 추가, 공정명 수정, 날짜·작업자·메모 입력을 허용한다. 확정 시 기존 일정을 교체하지 않고 선택된 후보만 추가하며 같은 규칙 ID의 기존 일정은 기본 제외한다.

## 화면과 상호작용

- 계약 현장 카드는 현장명, 상태, 공사기간, 진행률, 사용자 지정 현장색상만 표시한다.
- 공사 bar는 아이콘 없이 `현장명 · 공정명 · 작업자명`을 표시하고 현장색상을 사용한다.
- 여러 날 일정은 주가 바뀌어도 같은 schedule ID로 연결 bar를 렌더링한다.
- 상담, 실측, AS, 개인, 기타는 현장 없이 별도 일반 일정로 저장하고 공사 일정과 다른 시각 형태로 표시한다.
- 개별 일정을 편집할 때 전체 현장의 일정을 함께 보여주며 현재 편집 일정만 강조한다.
- 작업자는 자유 텍스트로 입력해 외부 작업자를 허용한다.

## 작업자 충돌

공백을 정리한 작업자명이 정확히 같고 `newStart <= existingEnd && newEnd >= existingStart`이면 충돌이다. 현재 편집 중인 동일 schedule ID는 제외한다. 경고에는 작업자명, 기존 현장, 기존 공정, 실제 겹치는 기간을 표시한다.

강제 저장은 새 권한을 만들지 않고 현재 인증 구조의 활성 `owner`에게만 제공한다. admin과 staff는 기존 권한 범위를 유지하며 충돌을 해소해야 저장할 수 있다.

## 공휴일

`schedule-holidays.js`는 대한민국 법정공휴일, 대체공휴일, 설날·추석과 확인된 공식 선거일을 읽기 전용 데이터로 제공한다. 외부 공급자는 선택적으로 병합하되 실패, CORS, 오프라인 시 내장 fallback만으로 달력과 일정 저장이 정상 동작한다. 공휴일은 사용자 일정 저장소에 기록하지 않는다.

## 반응형

- PC는 현장 카드와 큰 월간 달력을 표시한다.
- 768~1024px는 월간 달력을 유지하면서 카드와 정보 패널만 재배치하고 페이지 전체 가로 스크롤을 만들지 않는다.
- 640px 이하는 월간 달력을 억지로 축소하지 않고 agenda/list로 전환한다.
- 화면용 반응형 규칙은 기존 인쇄 결과에 영향을 주지 않는다.

## 검증

순수 모듈 자동 테스트에서 견적 선택, 공정 포함·제외, 전기·에어컨 분리, 마루 조건, 욕실 병합·순서, 후보 편집, 외부 작업자, 충돌 경계, owner 강제 저장, 공휴일 fallback, 현장 중복 방지, 기존 배열과 수동 현장·일정의 ID/개수/내용 보존을 검증한다.

실제 브라우저에서는 1440×900, 768×1024, 820×1180, 1024×768, 390×844, 430×932를 확인하고 전체 가로 overflow, 콘솔 오류, 카드, 연결 bar, 일반 일정, 모바일 agenda와 로컬/Supabase 동기화 회귀를 확인한다.
